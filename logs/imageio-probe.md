# ImageIO decode probe: Tiger vs modern ImageIO

## Update (2026-09-20, post ImageIO.pkg / RAW Camera / Security Update 2009-005)

The box got Apple's `ImageIO.pkg`, `RAWCamera.pkg`, and `SecUpd2009-005Intel.pkg` installed
(receipts in `/Library/Receipts/`, `/var/log/install.log` timestamp 21:59) and rebooted for the
security update. `ImageIO.framework`'s `CFBundleShortVersionString`:

|---|---|---|---|
| Before | 1.5.6 | 730,836 bytes | `sysroot/.../ImageIO.framework/Versions/A/{Resources/Info.plist,ImageIO}`, this repo's pre-update mirror of the box (dated 2026-09-19, before today's update) |
| After | 1.5.9 | 734,980 bytes | Read directly off the box just now |

(The 10.4u SDK's copy under `sdk/MacOSX10.4u.sdk/` has no `Resources/Info.plist` at all — it's a
link-only stub tree, not a real bundle, so it was never a usable "before" reference; the
`sysroot/` mirror was.)

Re-ran `spike/imageioprobe-tiger` unchanged (same binary, same 15 test images) on the
now-updated box: **byte-for-byte identical output** to the dump this file's findings are based
on (`diff` against the previously committed run: zero lines differ, 341/341 lines match). Every
finding below — the `CGImageSourceGetStatusAtIndex` trap, the stuck-at-`ReadingHeader`
progressive status for PNG/JPEG/GIF/TIFF, the PNG-compressed-ICO decode failure, the near-black
CMYK JPEG, the sRGB-ICC-profile pixel delta, the missing GIF dictionary on a no-loop-extension
GIF — is **unchanged** on 1.5.9. This 1.5.6 -> 1.5.9 update (RAW camera support plus a security
fix, going by the package names) did not touch the code paths this probe exercises.

WebCore's image decoding on this port goes entirely through Tiger's own ImageIO
(`compat/CG-SURVEY.md`: ImageIO is API-complete on Tiger — incremental decoding, all the
`CGImageSource*` entry points WebCore calls are native exports, nothing stubbed). This is a
bounded runtime probe of what Tiger's 2005 ImageIO actually *decodes*, compared pixel-for-pixel
against this Mac's modern ImageIO, for the formats and edge cases `ImageDecoderCG.cpp` exercises.

Tool: `spike/imageioprobe.c`, plain C, built once natively and once with `tiger-clang`, same
source, no `#ifdef`s (every `kCGImageProperty*` it reads is declared
`AVAILABLE_MAC_OS_X_VERSION_10_4_AND_LATER` in the 10.4u SDK's `CGImageProperties.h`, so both
builds see the same symbols). For each test image it decodes two ways — `CGImageSourceCreateWithData`
(whole-data) and `CGImageSourceCreateIncremental` + `CGImageSourceUpdateData` fed in 4 chunks
(mirroring `ImageDecoderCG`) — reads status/count/properties, creates each frame both with and
without `kCGImageSourceShouldCache`, draws it into a premultiplied-first 32-bit BGRA context (the
format `ImageDecoderCG`/`NativeImageCG` use), and prints a CRC32 of the pixel buffer plus RGBA at
5 fixed sample points. Test images generated by `spike/imageioprobe/gen_images.py` (Pillow +
ImageMagick, 32x32, in `spike/imageioprobe/images/`): 8-bit RGBA PNG, Adam7-interlaced PNG, 16-bit
grayscale PNG, paletted PNG with tRNS, 8-bit grayscale PNG, PNG with an embedded sRGB ICC profile,
baseline JPEG, progressive JPEG, CMYK JPEG, JPEG with EXIF orientation 6, a 3-frame animated GIF
(per-frame delays 100/250/400ms, disposal methods 2/1/1, loop=infinite), a GIF with a transparent
index and no Netscape loop extension, BMP, two-size ICO (16/32, PNG-compressed frames), TIFF.

Run: built native with system clang + `-framework CoreGraphics -framework ImageIO`; built for
Tiger with `tiger-clang -F compat/sdk-overlay -F .../ApplicationServices.framework/Frameworks
-ltigercompat -framework ApplicationServices` (same pattern as `spike/cgtest.c`); copied both the
binary and the images to the box over `scp -O`; ran both; `diff`'d the two dumps. **Zero crashes,
zero hangs, on any of the 15 images, in either the whole-data or incremental path.** Every image
produced plausible dimensions and pixels except the ICO (below).

## Results

| # | Case | Classification | Finding |
|---|---|---|---|
| 1 | `CGImageSourceGetStatusAtIndex` | (a) missing/broken, WebCore already routes around it | Always returns `kCGImageStatusUnknownType` on Tiger, for every format, at every index, even once the frame has fully decoded. See below — real impact only on non-last frames of animated images. |
| 2 | Progressive/incremental status for PNG, JPEG, GIF, TIFF, ICC-PNG | (a) missing feature | Overall `CGImageSourceGetStatus` sits at `kCGImageStatusReadingHeader` (not `Incomplete`) through every partial chunk short of the last, and `CGImageSourceGetCount` stays 0, even at 75% of the file. Jumps straight to `Complete`/final count on the last `CGImageSourceUpdateData(..., atEnd: true)`. Native ImageIO reports `Incomplete` with the right count as soon as the header is parsed (by 25% for these tiny files). |
| 3 | Progressive/incremental status for BMP | Not a gap | BMP does **not** show finding #2: Tiger reports `Incomplete`/count=1 by the first chunk (25%), matching native. BMP's fixed-size header decodes immediately; the gap in #2 is per-codec, not a framework-wide limitation. |
| 4 | ICO with PNG-compressed frames (16x16 + 32x32) | (c) failure | `CGImageSourceCreateImageAtIndex` returns `NULL` for both frames on Tiger; `CGImageSourceCopyPropertiesAtIndex` returns nothing (width/height unreadable). Native decodes both frames correctly. Tiger's ICO decoder predates the PNG-compressed icon format (a Vista-era, ~2007 addition); it only knows classic BMP/AND-XOR-mask ICO frames. |
| 5 | Single-frame GIF with a Graphic Control Extension (delay+transparency) but no `NETSCAPE2.0` loop extension | (a) missing property, low impact | Tiger's decoder surfaces **no** `kCGImagePropertyGIFDictionary` at all for this file (no delay, no loop count in the top-level properties), even though the GCE block is present in the bytes and Tiger decodes the pixels/transparency correctly. Native ImageIO synthesizes the dictionary from the GCE alone (`GIFDelayTime=0`, clamped up to a reported `0.1`) and defaults `GIFLoopCount=1`. |
| 6 | 3-frame animated GIF (has a `NETSCAPE2.0` extension) | Not a gap | `GIFLoopCount`, per-frame `GIFDelayTime`, and pixels for all 3 frames (including the disposal-2 frame) match natively in every field checked. |
| 7 | CMYK JPEG | (b) real pixel difference | Center sample: native `(136,123,115)`, Tiger `(0,0,0)`-ish (`(14,19,9)`/`(0,0,7)`/`(20,0,0)`/`(0,0,10)`/`(0,0,0)` at the 5 points) — Tiger renders the image almost entirely black. Max channel delta ~135. This is a real decode difference, not color management: Adobe-flavored CMYK JPEGs (the kind every encoder — including Pillow here — writes) store channel values *inverted*, and readers must detect that via the Adobe APP14 marker. Tiger's decoder is not applying that inversion for this file. Matches the survey's prediction (`compat/CG-SURVEY.md`: "CMYK JPEG support" listed as an expected legacy-ImageIO gap). |
| 8 | 16-bit grayscale PNG | (b) minor pixel difference | The 5 sample points (corners + center) are byte-identical, but the whole-buffer CRC32 differs (`5ec3d3ca` vs `0ad42607`). Both decoders downconvert 16-bit to 8-bit for the BGRA context; the difference is in the downconversion rounding elsewhere in the 32x32 gradient, not a structural failure. |
| 9 | Baseline JPEG, progressive JPEG, EXIF-oriented JPEG, palette+tRNS PNG | (b) minor pixel difference | All samples are within 1-4 of the native value per channel (e.g. baseline JPEG center: native `(132,132,124)`, Tiger `(131,130,126)`). Consistent with independent JPEG IDCT/dequantization implementations (Tiger's 2005 libjpeg-derived decoder vs. the modern one), not a color-management issue — same order of magnitude across every JPEG case, absent on the lossless formats. |
| 10 | PNG with embedded sRGB ICC profile | (b) real pixel difference, color management | Center sample: native `(131,131,128)`, Tiger `(112,112,109)` — max delta ~23, well above the JPEG rounding noise in #9. `CGImageGetAlphaInfo` also disagrees (native reports `NoneSkipLast`, Tiger reports plain `None`, i.e. Tiger drops the alpha channel bookkeeping for this opaque-but-ICC-tagged PNG). Reads as Tiger's ColorSync not round-tripping this Pillow-generated ICC profile the way modern ColorSync does. |
| 11 | Interlaced (Adam7) PNG | Not a gap | Confirmed interlaced in the file (`IHDR` interlace byte = 1). Tiger decodes it; no diff beyond the two systemic findings (#1, #2) and default DPI (#13). |
| 12 | `CGImageGetAlphaInfo` value on identical pixels (GIF frame 2, ICO N/A, TIFF, ICC-PNG) | Not a gap | Tiger frequently reports a different (but equally valid) `CGImageAlphaInfo` enumerator for the *same* logical layout (e.g. `NoneSkipLast` vs `None`, `Last` vs `First`) — cosmetic, since every draw in this probe goes through `CGContextDrawImage` into a fixed BGRA context regardless, and the resulting pixels match wherever the decode itself matches (#3, #6, #9's siblings, TIFF, BMP). Only worth knowing if any WebCore code branches on the *raw* `CGImageAlphaInfo` of a decoded source image rather than always normalizing through a draw. |
| 13 | Default DPI when a format doesn't encode one (BMP, RGBA PNG) | (a) differing default | Native ImageIO reports 96x96, Tiger reports 72x72. WebCore does not consult `kCGImagePropertyDPI*` for CSS layout (image intrinsic size is `PixelWidth`/`PixelHeight`, which agree everywhere), so this is unlikely to be reachable, but flagged in case something in `ImageDecoderCG.cpp` or a caller reads DPI. |

## The one finding worth fixing in the port

**`frameIsCompleteAtIndex` in `ImageDecoderCG.cpp` (Source/WebCore/platform/graphics/cg/ImageDecoderCG.cpp:539-546)**
already has a comment explaining why it avoids `CGImageSourceGetStatusAtIndex` for the last frame
of an image ("changes the return status value from kCGImageStatusIncomplete to
kCGImageStatusComplete only if index > 1 && index < frameCount() - 1... use
CGImageSourceGetStatus() instead"), and uses `CGImageSourceGetStatus()` (the overall, not
per-index, status) whenever `index == frameCount() - 1`. Every one of this probe's single-frame
images (PNG/JPEG/BMP/TIFF/ICO/single-frame GIF) has index 0 == frameCount()-1, so they always take
that path — and `CGImageSourceGetStatus()` (overall) reports correctly on Tiger (finding
confirmed: it never diverged from native for the *final*, whole-file-received state). **This
existing code already routes around Tiger's broken `CGImageSourceGetStatusAtIndex` for every
non-animated image**, so finding #1 is dormant for the overwhelmingly common case.

It stops being dormant for **any non-last frame of a multi-frame image** — i.e. any animated GIF
with more than one frame, once fully downloaded. `frameIsCompleteAtIndex(0)` and
`frameIsCompleteAtIndex(1)` of our 3-frame test GIF call `CGImageSourceGetStatusAtIndex(src, 0/1)`,
which this probe shows returns `kCGImageStatusUnknownType` on Tiger — never
`kCGImageStatusComplete` — regardless of how much data has arrived. **Every frame of an animated
GIF except the last will read as permanently incomplete on Tiger.** `frameHasAlphaAtIndex`
(ImageDecoderCG.cpp, right below) calls `frameIsCompleteAtIndex` too and would report `true` (has
alpha) unconditionally for those frames as a side effect. Downstream, `BitmapImageSource`/
`BitmapImage`'s frame-advance logic (not probed here — out of scope for an ImageIO-only spike, but
worth a follow-up check) is a plausible place for "never treats frame N<last as ready" to either
stall GIF animation on frame 0 or force a redecode every tick; recommend a WebCore-side check
(not a shim — the API's Tiger behavior is a known Apple quirk WebCore already has a workaround
pattern for) making `frameIsCompleteAtIndex` treat `kCGImageStatusUnknownType` from
`CGImageSourceGetStatusAtIndex` the same as it treats the last-frame case: fall back to
`CGImageSourceGetStatus()` once `m_isAllDataReceived` is true, for any index, on this port.

Finding #2 (progressive status stuck at `ReadingHeader`, real for PNG/JPEG/GIF/TIFF, not for BMP)
is a genuine capability gap, not a bug to route around: Tiger's ImageIO plugins for those formats
just don't do partial/incremental header-through-Incomplete reporting the way modern ones do.
`ImageDecoderCG::encodedDataStatus()` (ImageDecoderCG.cpp:348-372) will sit at
`EncodedDataStatus::Unknown` for the whole download and jump straight to `Complete`, so progressive
image sizing/painting during a slow load degrades to "nothing shown until the image finishes
downloading" for every format except BMP. No shim exists for this — it is Tiger's actual decoder
behavior, not an ABI mismatch — so the fallback is graceful degradation already built into
`ImageDecoderCG`'s state machine (it has no other path but `Unknown`), not new code.

## Recommendation summary

- No CG/ImageIO API-surface shim is needed; `compat/CG-SURVEY.md`'s "ImageIO already there"
  assessment holds — everything WebCore calls exists and returns real data.
- One WebCore-side robustness fix is worth making: extend `frameIsCompleteAtIndex`'s existing
  last-frame workaround for `CGImageSourceGetStatusAtIndex` to every index once
  `m_isAllDataReceived`, or this port's animated GIFs will never advance past frame 0/1's
  "incomplete" state. Cheap, and matches the workaround pattern already in that function.
- Expect, and do not chase, pixel deltas of 1-4 per channel on every JPEG (finder #9) — different
  1990s-vintage vs modern IDCT/dequant implementations, present on every JPEG test case uniformly.
- Two real gaps to log and skip rather than fix: PNG-compressed ICO frames fail outright on Tiger
  (#4 — WebCore/apps on this port should not rely on modern-style ICO favicons with embedded PNG;
  classic BMP-frame ICOs were not tested here and are a natural follow-up), and CMYK JPEGs decode
  as near-black (#7, likely missing Adobe-inverted-CMYK handling) — both pre-existing Tiger ImageIO
  limitations with no shim surface (`CGImageSourceCreateImageAtIndex`'s internals are not
  something `compat/cgcompat.c` can reach into).
- The ICC-profile color divergence (#10) is real and larger than JPEG rounding noise; worth a
  closer look if the port ever ships ICC-tagged images, but out of scope for this pass (would need
  ColorSync-level tracing, not an ImageIO-level probe).

## Reproduce

```
python3 spike/imageioprobe/gen_images.py                       # regenerate the 15 test images
clang -O1 -o build/imageioprobe-native spike/imageioprobe.c \
  -framework CoreFoundation -framework CoreGraphics -framework ImageIO
toolchain/bin/tiger-clang -O1 -o build/imageioprobe-tiger spike/imageioprobe.c \
  -F compat/sdk-overlay \
  -F sdk/MacOSX10.4u.sdk/System/Library/Frameworks/ApplicationServices.framework/Frameworks \
  -ltigercompat -framework ApplicationServices
./build/imageioprobe-native spike/imageioprobe/images/* > /tmp/native.txt
ssh tiger mkdir -p /tmp/iioprobe/images
scp -O build/imageioprobe-tiger tiger:/tmp/iioprobe/
scp -O spike/imageioprobe/images/* tiger:/tmp/iioprobe/images/
ssh tiger '/tmp/iioprobe/imageioprobe-tiger /tmp/iioprobe/images/*' > /tmp/tiger.txt
diff /tmp/native.txt /tmp/tiger.txt
```
